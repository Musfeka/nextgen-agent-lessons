Agent Skills · Unit 1 of 10

What is an Agent?

And what makes it different from the chatbot you already use?

Time 12 minutes You will be able to name any AI task as prompt, tool, Skill, workflow or agent Prerequisites none

Almost everyone on your team has used a chatbot. Almost nobody has used an agent. The gap between those two things is the whole subject of this course — and it is smaller and more practical than the word "agent" makes it sound.

1.1 The ladder your team is standing on

There is a progression here, and each rung adds exactly one thing. Most confusion about AI comes from people standing on different rungs while using the same word.

Rung 1
Automation

Fixed rules, written by a human, run by a machine. A Jira workflow that moves a ticket when a box is ticked. No judgement.

Rung 2
Chatbot

Judgement, but no hands and no memory of your world. It answers. You do everything else.

Rung 3
Copilot

Sits inside your work — your document, your code — and suggests. You still drive every step.

Rung 4
Agent

Given a goal, it decides its own next steps, uses tools, sees what happened, and adjusts. It drives.

Notice that "agentic workflow" is not a fifth rung. It sits between 3 and 4, and it is where most useful work actually gets done. Unit 7 returns to this.

The step from rung 3 to rung 4 is the one that matters, and Anthropic draws the line precisely. There are two kinds of system that both get called "agentic":

Workflows are systems where LLMs and tools are orchestrated through predefined code paths. Agents are systems where LLMs dynamically direct their own processes and tool usage, maintaining control over how they accomplish tasks.

Anthropic, Building Effective AI Agents

The difference is who decides the next step. In a workflow, a programmer decided in advance. In an agent, the model decides in the moment.

The thing worth remembering

Neither is better. Anthropic's own advice is to prefer the simpler one: "consider adding complexity only when it demonstrably improves outcomes." A fixed six-step process that works is worth more than a clever agent that surprises you. Your team will be tempted to reach for the most autonomous option. Push back.

1.2 The six things an agent does

Strip away the vocabulary and every agent is doing the same loop. You already do this loop yourself, dozens of times a day.

Goal→ Context→ Reasoning→ Decision→ Action→ Feedback↺

Take a real one. A Senior SQA is told "regression-test the checkout change before Friday."

  • Goal — ship a tested checkout change by Friday.
  • Context — the ticket, the existing test suite, what broke last time.
  • Reasoning — payment paths are the risk; the shipping module is untouched.
  • Decision — run the payment regression pack first.
  • Action — actually open the tool and run it.
  • Feedback — three failures appear, two are environment noise. Adjust and go again.

A chatbot can do the middle four. It cannot do Action, and because it cannot act, it never gets real Feedback — only your description of what happened. That is the entire difference, and it is why agents feel qualitatively different to use.

Where this bites

Because an agent acts, its mistakes are no longer just wrong text on a screen. They are edited files, sent messages, changed records. Unit 4 covers permissions and Unit 8 covers human approval. Do not let anyone on your team skip those two.

1.3 So what is an Agent Skill?

Here is the definition this whole course hangs on:

Definition

An Agent Skill is a reusable package of instructions that teaches an agent how your organisation performs a specific kind of work — loaded automatically, only when it is relevant.

Anthropic's framing is the most useful one I have found for a mixed audience:

Building a skill for an agent is like putting together an onboarding guide for a new hire.

Anthropic, Equipping agents for the real world with Agent Skills

That analogy does a lot of work. A new BA joining your team is already smart. You do not teach them what a requirement is. You teach them your template, your definition of done, the client who always forgets to mention compliance, and the three questions you must ask before writing a single user story. That — and only that — is what belongs in a Skill.

This is the single most common beginner mistake, and it appears in Unit 5 again with teeth: people write Skills that explain things the model already knows. It wastes the budget and makes the Skill worse, not better.

What it actually looks like

Concretely — and this is deliberately unglamorous — a Skill is a folder with a Markdown file in it.

requirement-analysis/SKILL.md 
---
name: analyzing-requirements
description: Analyzes a business requirement for gaps, ambiguity and missing
  acceptance criteria using the team's standard checklist. Use when the user
  shares a requirement, BRD, or feature request and wants it reviewed.
---

# Analyzing requirements

## Process
1. Classify the requirement: functional, non-functional, or business rule.
2. Check it against the ambiguity checklist below.
3. List every gap as a question addressed to the requester.

## Ambiguity checklist
- Who is the actor? (never accept "the user")
- What happens on failure?
- Is there a compliance or audit implication?

That is a complete, working Skill. Two required fields at the top, plain instructions below. There is no code in it, and nothing in it requires you to be a developer.

Spec detail

Only name and description are required. name is capped at 64 characters, lowercase letters, numbers and hyphens only. description is capped at 1,024 characters. Full rules live in the SKILL.md anatomy reference.

1.4 The distinction that unblocks everything

Four words get used interchangeably by people who should know better. Getting them straight is the tangible win of this unit.

The four things, and the question each one answers
ConceptAnswers the questionLifespanFrom your world
Prompt What do I want right now? One conversation "Summarise this meeting transcript."
Tool What can the agent reach? Permanent capability Read Jira. Search the repo. Send an email.
Skill How do we do this kind of work? Reused indefinitely "Our way of writing acceptance criteria."
Workflow In what order do the steps run? Defined in advance Requirement → story → criteria → test cases.
Agent Who is deciding? Runs the loop Picks the Skill, calls the tool, checks the result.

The compressed version, worth memorising: a tool is access, a Skill is method, a prompt is a request, a workflow is order, an agent is judgement.

The same distinction, in six jobs
BA
Tool: read Confluence. Skill: our requirement gap-analysis method. Prompt: "check this BRD."
SQA
Tool: read the test management system. Skill: how we derive test scenarios from criteria. Prompt: "cover this story."
UX
Tool: read the research repository. Skill: our heuristic review rubric. Prompt: "critique this screen."
Dev
Tool: read the codebase. Skill: our code review standards. Prompt: "review this pull request."
PM
Tool: read the project plan. Skill: how we write a status report. Prompt: "draft this week's update."
BD
Tool: read the CRM. Skill: our RFP qualification method. Prompt: "should we bid on this?"
