How Agents Think and Act

What is actually happening between your request and the result?

Time 12 minutes You will be able to decompose a real request into the steps an agent must take Prerequisites Unit 1

In Unit 1 you learned that an agent decides its own next step. This unit opens the box. You need this model for one reason: when a Skill misbehaves later, you cannot fix it unless you know which part of the loop broke.

2.1 The building block: an LLM with augmentations

Start smaller than "agent." The unit everything is made from is a model that has been given three extra things:

Retrieval

It can go and fetch information it was not given — search a repo, read a document.

Tools

It can take actions in the world — write a file, call an API, run a command.

Memory

It can carry things forward — notes, prior results, state across steps.

Anthropic calls this the augmented LLM, and it is the foundation of every agentic system. Crucially, the model itself now generates its own search queries and picks its own tools — you are not scripting those choices.

This is why "just write a better prompt" stops being sufficient. Once a model is choosing its own actions, you are shaping judgement, not output. That is what a Skill does.

2.2 Perception — what actually reaches the agent

An agent perceives nothing except what lands in its context window. This sounds obvious and is the source of perhaps half of all agent failures.

The most expensive misunderstanding on this course

The agent does not know about your project. It does not know last sprint's decision, the client call, the reason that field is nullable, or the standard everyone follows but nobody wrote down. It knows what is in front of it, right now, and nothing else.

When a team member says "the AI got it wrong," the honest question is almost always: could anyone have got it right, given only what we gave it?

What can land there: your request, documents, images, data, the state of a system, and what has already happened in this session. Unit 3 is entirely about curating that set deliberately.

2.3 Reasoning and planning

Reasoning is the compressed version of understand → analyse → decide. Planning is what happens when the goal is too big for one action: the agent breaks it into smaller pieces first.

The practical consequence for you is about transparency. Anthropic's guidance lists "prioritize transparency through explicit planning steps" as one of three core implementation principles. An agent that states its plan before acting is one you can interrupt at the right moment. An agent that silently does nine things is one you audit afterwards, which is worse and later.

2.4 Action, and the thing that makes agents work

Action is the rung-4 capability from Unit 1: tools, APIs, files, applications, search, running code. But the important part is not the acting. It is what comes back.

Agents … execute while receiving "ground truth" feedback from the environment (tool results, code execution) … The process is typically just LLMs using tools based on environmental feedback in a loop.

Anthropic, Building Effective AI Agents

Ground truth is the phrase to hold onto. When an agent runs a test and the test fails, that failure is not an opinion. It is reality pushing back. This is why agents are dramatically more reliable at tasks with a checkable result — code that compiles, a query that runs, a file that validates — than at tasks where nothing can disagree with them.

Design implication you will use in Unit 6

If you can give your Skill something that can fail — a checklist to verify against, a validation step, a rule that can be violated — you have converted a task with no feedback into a task with feedback. That single move improves output quality more than any amount of prompt polishing.

2.5 The loop

Observe→ Think→ Act→ Observe→ Adjust↺

Two properties of this loop matter enormously in practice.

It has a stopping condition. Agents pause for human input at checkpoints, or when blocked. Left without limits, a loop is a way to spend money and do damage quickly. Where the stop goes is a design decision — Unit 8.

Every pass through it costs context. Each observation lands in the window and stays there. This is why long agent runs degrade, and why Unit 3 treats context as a budget rather than a container.

Worked example: "Prepare a test plan for this feature"

This is the activity from your outline. Here is the decomposition, so you can see the standard before doing your own.

  1. Read the feature
    Fetch the ticket and any linked spec. Perception. Without this the agent invents a feature.
  2. Find what already exists
    Search the test repository for related coverage. Retrieval. Skipping this is how you get 40 duplicate test cases.
  3. Identify the risk surface
    What changed, what touches it, what broke here before. Reasoning — and the step most dependent on team knowledge a Skill would supply.
  4. Decide scope
    Which areas get deep coverage, which get a smoke check. Decision. A judgement call your standards should constrain.
  5. Draft scenarios, then cases
    Two passes, not one. Action.
  6. Check against acceptance criteria
    Every criterion traced to at least one case. Feedback — this step can fail, which makes it valuable.
  7. Hand to a human
    A Senior SQA approves scope before anyone executes. Stopping condition.

Notice steps 3, 4 and 6. Those are the ones where a generic model does adequately and your team's Skill would do well. That is where the value of Skills lives.

Why the last rubric item matters most

If your decomposition has no step that could fail, you have described a task with no ground truth. That is not a reason to abandon it — but it tells you the Skill will need a human check, and it tells you exactly where to put it.
