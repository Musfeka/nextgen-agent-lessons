What Exactly Is an Agent Skill?

From a one-off instruction to a capability your whole team can rely on.

Time 18 minutes You will be able to read a real SKILL.md and judge whether it is any good Prerequisites Unit 4

Everything so far has been preparation. This is the unit where the abstraction becomes a file you can open, and where the four ideas you have collected — context budget, right altitude, ground truth, tool-versus-method — turn out to have been about Skills the whole time.

5.1 The mechanism: progressive disclosure

Before the anatomy, understand the trick that makes Skills work. It is the direct answer to Unit 3's problem: context is finite, but your organisation's knowledge is not.

Skills solve this by loading in three stages.

The three levels of a Skill — from the Agent Skills documentation
LevelWhatWhen loadedCost
1 · Metadata name and description Always, at startup ~100 tokens per Skill
2 · Instructions The body of SKILL.md Only when triggered Under 5k tokens
3 · Resources Bundled files and scripts Only when referenced Nothing until accessed

Read that table twice. It has three consequences that shape every design decision you will make:

  1. You can install a hundred Skills without penalty. Until one is triggered, it costs about a hundred tokens. This is why a library of narrow Skills beats one enormous one.
  2. The description is the whole trigger. It is the only part the model sees when deciding. A perfect Skill body with a vague description never runs.
  3. Bundled content is effectively free. Scripts are executed rather than read, so only their output costs tokens. A Skill can carry a 300-page reference and pay nothing until the day it needs page 41.

This is what Anthropic means by Skills being "effectively unbounded" in scope while staying context-efficient. The library grows; the budget does not.

5.2 Anatomy — what the spec requires, and what good practice adds

The spec is smaller than people expect

A Skill is a directory containing a SKILL.md file. That file must have YAML frontmatter with exactly two required fields: name and description. Everything else is Markdown of your choosing.

test-scenario-generation/SKILL.md 
---
name: generating-test-scenarios
description: Derives test scenarios from acceptance criteria using the team's
  risk-based coverage model, and flags criteria that cannot be tested as
  written. Use when a user story, acceptance criteria or feature spec needs
  test coverage designed.
---

# Generating test scenarios

## Process
1. Extract every acceptance criterion as a separate line.
2. Classify each: happy path, alternate path, error path, or non-functional.
3. Apply the coverage rule below.
4. Flag any criterion that is untestable as written — do not invent one.

## Coverage rule
- Error paths always get a scenario. Always.
- Happy paths get one scenario each.
- Non-functional criteria get a scenario only if a threshold is stated.

## Output
A table: ID | Criterion | Type | Scenario | Rationale.
One row per scenario. No prose before or after the table.

That is a complete, professional Skill. Note what it does not contain: no explanation of what a test scenario is, no definition of "happy path," no encouragement to be thorough. All of that is knowledge the model already has. Every line present is something only your team knows.

The fourteen questions a good Skill answers

Your outline lists fourteen elements. They are not spec fields — you will not find them in the documentation. They are a design checklist, and that is more useful: they are the questions to ask while drafting, answered in ordinary Markdown.

ElementWhere it livesAsk yourself
Purposedescription, first clauseWhat work does this do?
Triggerdescription, "Use when…"How will Claude know to reach for it?
RoleBody, opening lineWhose standards apply?
InputsBodyWhat must be present for this to work?
ContextBody, or a bundled fileWhat does it need to know that only we know?
InstructionsBodyWhat is the method?
RulesBody, stated as must/neverWhat is non-negotiable?
ProcessBody, numbered stepsIn what order?
Decision logicBody, conditional sectionWhere does it branch, and on what?
ToolsBody, named explicitlyWhat must it be able to reach?
Output formatBody, as a templateWhat shape is the deliverable?
ExamplesBody, or examples.mdWhat does good look like?

Do not turn this into a template with fourteen headings

The temptation is to make every Skill a form with all fourteen sections filled in. That produces bloated Skills that violate the concision principle. These are questions to answer, and many are answered in a single line or not needed at all. The example above answers nine of them in twenty lines.

5.3 The description field, in detail

If you take one thing from this unit, take this. Skill selection lives or dies here.

Good — what + when
description: Extract text and
tables from PDF files, fill
forms, merge documents. Use
when working with PDF files
or when the user mentions
PDFs, forms, or document
extraction.
Bad — no trigger, no terms
description: Helps with
documents


description: Processes data


description: Does stuff
with files

Three rules from the authoring guidance, all of which your team will break at first:

  • Always third person. "Processes Excel files and generates reports" — not "I can help you…" or "You can use this to…". The description is injected into the system prompt, and mixed point-of-view causes real discovery problems.
  • Say what it does and when to use it. Both halves. The second half is the one people omit.
  • Include the words people actually type. If your BAs say "BRD," the word BRD belongs in the description. Matching happens on this text.
Hard limits

name: max 64 characters; lowercase letters, numbers and hyphens only; no XML tags; cannot contain the reserved words "anthropic" or "claude". Gerund form is recommended — analyzing-requirements over requirement-helper.

description: non-empty, max 1,024 characters, no XML tags.

5.4 Good Skill, bad Skill

The single biggest quality lever is concision, for the reason you learned in Unit 3: the context window is shared. Anthropic's framing is that "the context window is a public good" and the default assumption should be that Claude is already very smart.

Good — ~50 tokens
## Extract PDF text

Use pdfplumber:

import pdfplumber
with pdfplumber.open("f.pdf") as pdf:
    text = pdf.pages[0].extract_text()
Bad — ~150 tokens
## Extract PDF text

PDF (Portable Document Format)
files are a common file format
that contains text, images and
other content. To extract text
you'll need a library. There are
many libraries available, but
pdfplumber is recommended
because it's easy to use…

Challenge every paragraph you write with three questions from the authoring guide: Does Claude really need this explanation? Can I assume Claude knows this? Does this paragraph justify its token cost?

Degrees of freedom — the other quality lever

Match specificity to how fragile the task is. The published analogy is a robot on a path:

High freedom
Open field

Many routes work. Give direction, not steps. "Analyse structure, check for edge cases, suggest improvements." Use for code review, critique, analysis.

Medium freedom
Marked trail

A preferred pattern exists, variation is fine. Give a template with parameters. Use for report generation, structured drafting.

Low freedom
Narrow bridge

Cliffs on both sides. Give the exact command and forbid deviation. "Run exactly this. Do not add flags." Use for migrations, releases, anything irreversible.

Most beginner Skills use low freedom everywhere, because it feels safer. It is not — it is brittle (Unit 3), and it wastes tokens specifying things that did not need specifying.

5.5 Atomic Skills and boundaries

Because Level 1 costs almost nothing, the economics favour many narrow Skills over one broad one.

One Skill: "QA Assistant"

Does everything related to QA. Triggers on almost any QA-adjacent request, then loads a huge body of instructions of which 80% is irrelevant to the task at hand.

Impossible to test, impossible to improve without risking everything else.

Four Skills

classifying-requirements
analyzing-requirement-gaps
generating-test-cases
reviewing-test-cases

Each triggers precisely, loads only what it needs, and can be improved or retired alone.

The boundary test: if you cannot write a description that clearly excludes the neighbouring Skill, your boundary is in the wrong place. Two Skills that both plausibly match the same request will be selected unpredictably.

Reusability

A Skill must work with different inputs — that is the whole point. The test: could a colleague use this next month, on a different project, without editing the file? If it only works on the document you had open when you wrote it, you have written a prompt with extra steps.

Avoid time-sensitive content

Never write "before August, do X; after August, do Y." It will be wrong and nobody will notice. If you must record superseded practice, put it in a collapsed "Old patterns" section at the bottom.
