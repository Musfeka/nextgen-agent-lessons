Tools, Actions and Capabilities

How does an agent actually do things — and what stops it doing the wrong ones?

Time 13 minutes You will be able to map the tools a task needs and classify each one's risk Prerequisites Unit 3

An agent that can only generate text is a very good writer. An agent that can act is a colleague — and a liability. This unit is the shortest path to using the second kind safely.

4.1 What a tool is

A tool is a defined capability the agent can invoke to reach beyond the conversation: read a file, query a database, search the web, run a script, send a message, open a ticket.

Two things about tools surprise people:

  • The agent chooses. You do not call the tool. You make it available and describe it; the model decides whether, when, and with what arguments.
  • The description is the interface. A tool the model does not understand is a tool it will use wrongly or ignore. Tool documentation is not documentation — it is programming.

Effective tools are self-contained, robust to error, and extremely clear with respect to their intended use.

4.2 Tool versus Skill — the distinction that keeps mattering

You met this in Unit 1. Here it is sharpened, because this is where people design badly.

Skill = method

How we analyse a software requirement.

Knowledge, standards, sequence, judgement. Portable. Survives a change of systems.

Tool = reach

Read Jira. Read GitHub. Query the database.

Access to a system. Says nothing about what good work looks like.

Neither is sufficient. A Skill with no tools can reason about material you paste in, but cannot go and get it. Tools with no Skill can fetch everything and still produce work that fails your review.

A test you can apply in seconds

If your company switched from Jira to Azure DevOps tomorrow — would this thing need rewriting? If yes, it is a tool concern. If no, it is a Skill concern. Keep them in separate boxes and both stay maintainable.

4.3 How the agent chooses a tool

Three decisions, every time: which tool, when, and with what arguments. The model makes them by reading the available tool descriptions and matching them against its current goal — exactly the way it matches a Skill's description.

Which means the failure mode is identical, too:

Bloated tool sets

Anthropic is blunt about this: a common failure is "bloated tool sets that cover too much functionality or lead to ambiguous decision points about which tool to use."

And the diagnostic test: if your engineers cannot definitively say which tool is correct for a situation, neither can the agent. Ambiguity you can live with is ambiguity the model cannot.

This is the strongest argument against "connect everything and see what happens." Twelve overlapping integrations do not make an agent twelve times more capable. They make its tool choice unreliable.

4.4 Tool chains

Real work is a sequence. Here is the SQA example from your outline, with the important part marked:

Read requirement→ Search existing tests→ Analyse gap→ Create test cases

Three of those four steps are tool calls. The highlighted one is not — it is judgement, and no integration will supply it. That step is where your Skill lives.

Generalise this and you have a design habit worth teaching your whole team: draw the chain, then circle the steps that are not tool calls. Those circles are your Skill backlog.

4.5 Tool safety

The moment an agent can act, four questions stop being theoretical.

Classify every tool before you enable it
QuestionWhat you are decidingGet it wrong and…
PermissionWhat may it touch at all?It reaches data it should never have seen.
Read or writeCan it change anything?A wrong answer becomes a wrong record.
ValidationIs the action checked before it lands?Errors are found by customers, not by you.
ApprovalDoes a human confirm first?Nobody notices until it is 200 rows deep.

The read/write line is the one to teach hardest

It is the cheapest safety control you have, and it is comprehensible to non-technical staff.

Read — start here always

Search the repo, read the ticket, query the report, fetch the document.

Worst case: a wasted run and a wrong answer you can discard.

Write — earn this

Update the ticket, send the email, commit the change, post to the client.

Worst case: something outside your control, already seen by someone else.

A sane rollout for a team new to this: read-only for everyone, writes behind explicit approval, destructive actions not enabled at all until someone owns them.

And a specific warning about Skills themselves

Skills are executable trust

The documentation is explicit: "Use Skills only from trusted sources." A Skill can direct an agent to invoke tools in ways that do not match its stated purpose. Treat installing a third-party Skill exactly like installing software from the internet — read every file first, including bundled scripts.

Skills that fetch content from external URLs deserve particular suspicion: fetched content can itself carry instructions.
