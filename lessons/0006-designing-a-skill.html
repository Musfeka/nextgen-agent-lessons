Designing and Building a Skill

How do I create a good one — rather than a plausible-looking one?

Time 20 minutes + build You will be able to build, install and iterate on a real working Skill Prerequisites Unit 5

Unit 5 taught you to read a Skill. This unit is about producing one, and it opens with the piece of advice that most changes outcomes — and that almost everyone skips.

6.1 Build your evaluations first

The instruction that reorders everything

"Create evaluations BEFORE writing extensive documentation. This ensures your Skill solves real problems rather than documenting imagined ones."

The natural instinct is to write the Skill, then check whether it works. Invert it. The published sequence is:

  1. Identify gaps
    Run Claude on real tasks with no Skill. Write down exactly what it got wrong or had to be told.
  2. Create evaluations
    Build three scenarios that test those specific gaps.
  3. Establish a baseline
    Record how it performs without the Skill. This is what you will compare against — and what you will show your team in Unit 10.
  4. Write minimal instructions
    Just enough to close the gaps. Not a document — the smallest thing that passes.
  5. Iterate
    Run the evals, compare to baseline, refine.

Why this matters so much for your team: without a baseline, nobody can tell whether a Skill helped. Step 3 is the difference between "this feels better" and a demonstrable before/after.

An evaluation here is not automated testing. There is no built-in runner — the docs say so explicitly. It is three saved inputs and a written statement of what a good response would contain. That is enough.

6.2 The design sequence

Identify→ Define→ Contextualise→ Design→ Implement→ Test→ Evaluate→ Improve↺

Identify — pick the right task

Three conditions. A candidate that fails any of them will disappoint you.

  • Repetitive. You do it often enough that the setup cost pays back.
  • Knowledge-intensive. Doing it well requires something not in the model — your standards, your domain, your client.
  • Checkable. Somebody can tell whether the output is good. (Unit 2's ground truth, returning.)

Define — goal, inputs, outputs

Write these three lines before anything else. If you cannot, the Skill is not scoped yet.

GOAL:    Derive test scenarios from acceptance criteria.
INPUT:   A user story with acceptance criteria. Nothing else required.
OUTPUT:  A table — ID, criterion, type, scenario, rationale.

Be strict about INPUT. "Whatever the user happens to have" is not an input specification, and it is the reason many Skills behave inconsistently.

Contextualise — what does it need to know that Claude does not?

Run the Unit 3 test on every candidate line: is this knowledge (already in the model, free) or context (yours, worth paying for)? Keep only the second kind.

Design — structure, rules, decisions, failure

Four questions, in this order:

Process

What are the steps, numbered, in order? Use a checklist if there are more than four.

Rules

What must always or never happen? Say must and never — not "try to".

Decisions

Where does it branch? On what signal? What happens in each branch?

Failure

What should it do when it cannot proceed? Guess, or stop and ask?

The most-skipped section, and the most valuable

Failure handling. If you do not say what to do when information is missing, the model will do the reasonable thing: proceed with a sensible assumption. That is exactly what you do not want from a compliance review or a test plan.

Write it explicitly: "If the acceptance criteria do not state a failure behaviour, flag it as untestable. Never invent one."

Implement — the patterns worth knowing

Workflows with checklists. For anything with more than about four steps, give a checklist the agent copies into its response and ticks off. This measurably prevents step-skipping — particularly of validation steps, which are the ones it is most tempting to skip.

## Test design workflow

Copy this checklist and track your progress:

- [ ] Step 1: Extract every acceptance criterion separately
- [ ] Step 2: Classify each by type
- [ ] Step 3: Apply the coverage rule
- [ ] Step 4: Flag untestable criteria
- [ ] Step 5: Verify every criterion appears in the table

Feedback loops. The pattern is run a check → fix → repeat, and it works without any code. The "validator" can simply be a reference document:

1. Draft the scenarios following the coverage rule.
2. Review against the checklist in STANDARDS.md.
3. If issues found: note each one, revise, review again.
4. Only proceed when every item passes.

This is the highest-leverage pattern in the whole course for non-technical roles. It manufactures ground truth where there was none.

Progressive disclosure. Keep SKILL.md under 500 lines. When it grows, split — and keep every reference exactly one level deep:

One level deep
SKILL.md
 ├→ standards.md
 ├→ examples.md
 └→ reference/domain.md

Everything links directly from SKILL.md. Files get read completely.

Nested — avoid
SKILL.md
 └→ advanced.md
      └→ details.md
           └→ the actual info

Claude may only preview nested files, giving incomplete information.

And for any reference file over 100 lines, put a table of contents at the top — so a partial read still reveals the full scope of what is available.

Where the file actually goes

Claude Code

Filesystem-based, no upload needed. Personal: ~/.claude/skills/your-skill-name/SKILL.md. Project (shared through the repo): .claude/skills/your-skill-name/SKILL.md. Claude discovers them automatically.

claude.ai: upload a zip via Settings → Features. Per-user only — each colleague uploads their own copy, and admins cannot distribute centrally. API: upload via the Skills API; shared workspace-wide.

Skills do not sync between these surfaces. Pick one for your rollout. This matters for Unit 10 — see the note there.

6.3 Iterate with two Claudes

This is the working method the documentation recommends, and it is unintuitive enough to be worth naming explicitly.

  • Claude A — your collaborator. Helps write and refine the Skill.
  • Claude B — a fresh session with the Skill installed, doing real work.

You watch B, and bring what you observe back to A. Not "make this Skill better" — but "when Claude used this Skill, it forgot to filter by date for Q4. Should we add a section on date filtering?" Concrete observed failures produce good revisions; abstract requests produce longer documents.

You do not need a special prompt for this

Claude understands the Skill format natively. Ask it to create a Skill and it will produce correct frontmatter and structure. Your job is not to explain the format — it is to supply the domain expertise and then cut. Expect to delete a third of what it writes with "remove the explanation of what a test scenario is — Claude already knows that."

What to watch for while observing

  • Unexpected paths — reads files in an order you did not expect? Your structure is less intuitive than you thought.
  • Missed connections — never follows a reference? The link needs to be more prominent.
  • Overreliance — reads the same bundled file every single time? It belongs in SKILL.md.
  • Ignored content — never opens a file at all? Delete it, or signal it better.
