Skill Composition and Agent Workflows

How do multiple Skills work together on one real piece of work?

Time 16 minutes You will be able to map a work process into a SkillGraph with the right pattern per edge Prerequisites Unit 6
Read this first — what kind of unit this is

Units 1–6 taught documented behaviour. This unit is synthesis. "SkillGraph" is not an Anthropic term and there is no official specification for composing Skills. What follows maps the five documented workflow patterns from Building Effective AI Agents onto Skills, plus your own framing.

It is sound and useful — but when you teach it, label it as your model, not as spec. Your technical people will respect the distinction, and it protects your credibility on everything else.

7.1 One request, several Skills

Real work rarely fits one Skill. Your outline's example is the canonical one:

Business requirement→ Requirement analysis→ User story→ Acceptance criteria→ Test scenario→ Test case→ Test review

Six Skills, each atomic, each independently useful. Together they cover a process that currently takes your team days and three handovers.

Why composition is automatic, not configured

You do not wire these together. Each Skill's description declares when it applies; the agent selects as the work moves. Composition emerges from good descriptions.

Which is why Unit 5 hammered the boundary test: if two descriptions overlap, composition becomes unpredictable. Sloppy boundaries do not fail visibly — they fail as inconsistency.

7.2 The five relationships between Skills

Composition patterns, and the documented workflow pattern each corresponds to
PatternShapeUse whenDocumented as
Sequential A → B → C Each step needs the previous one's output. Fixed order. Prompt chaining
Conditional A → (B or C) The input type decides what happens next. Routing
Parallel A → B and C → merge Independent work, or several views of the same thing. Parallelization
Delegated A → {B…n} → A The number of subtasks is not known in advance. Orchestrator-workers
Reviewed A ⇄ B, looping Clear criteria exist and iteration measurably improves output. Evaluator-optimizer

Sequential — the default

The requirement chain above. The essential design question is what passes between stages. A handover that loses the rationale ("why is this criterion here?") produces test cases nobody can defend. State the handoff format in each Skill's output section.

Conditional — routing by input

"If the requirement is a business rule, use the rule-extraction Skill. If it is non-functional, use the NFR Skill." This is where atomic Skills earn their keep — routing is only possible when the destinations are distinct.

Parallel — two flavours

  • Sectioning — genuinely independent subtasks at once. A PM's risk analysis and dependency analysis do not need each other.
  • Voting — the same task several times for confidence. Three independent security reviews of one change catch more than one review does.

Delegated — when you cannot know the shape in advance

"Analyse this 90-page RFP" — nobody knows how many sections need deep work until it is opened. A coordinating agent decides, dispatches, and synthesises. Anthropic's own account of building this at production scale is in How we built our multi-agent research system, including what went wrong; worth reading before you promise it to anyone.

There is a real cost here. Sub-agents each burn their own context and return a condensed summary — powerful, but multiplying token spend. Use when the task genuinely cannot be predicted, not because it sounds sophisticated.

Reviewed — the pattern with the best return

One Skill produces, another critiques against explicit criteria, the first revises. The reviewing-test-cases Skill at the end of the chain is not decoration — it is the loop that manufactures ground truth for work that otherwise has none. If you build only one composition pattern, build this.

7.3 Prerequisites and dependencies

Some Skills genuinely cannot run without a predecessor's output. generating-test-cases needs acceptance criteria to exist.

There is no dependency declaration in the format. You express it in two ordinary ways:

  • In the description — scope the trigger: "Use when acceptance criteria are available."
  • In the body, as failure handling — "If no acceptance criteria are present, stop and say so. Do not infer them."

That second line is doing dependency management with nothing but a sentence, and it is the reason Unit 6 pushed failure handling so hard.

7.4 The agent as orchestrator

Here is the conceptual shift your outline correctly identifies as the important one:

The agent doesn't need to know everything. It needs to know which capability to invoke and when.

Your outline — and it is exactly right

This reframes what you are building. You are not making the agent smarter. You are building an organisation's capability library and letting the agent route through it. The agent supplies judgement about which; your Skills supply the standards for how.

The restraint clause

Everything in this unit is more complex than a single Skill, and the published guidance is unambiguous: "consider adding complexity only when it demonstrably improves outcomes."

Most teams should build three good atomic Skills and one review loop before touching delegation or parallelism. Composition that emerges from clean boundaries is free. Composition you engineer is not.

Retrieval check

1How do several Skills end up being used on one request?

2A PM wants risk analysis and dependency analysis on the same plan. Neither needs the other's output. Which pattern?

Activity: draw your SkillGraph

Take one real process from your team — end to end, across handovers if it crosses them. Write each node as a Skill name in gerund form, and label each edge with its pattern.

Then cut it down

Whatever you drew, find the two adjacent nodes with the most pain between them and build only those, with a review loop. A ten-node graph on paper and zero Skills installed helps nobody. Two working Skills and a demonstrable before/after changes minds.
