Agent Memory & Persistence

How does an agent remember useful information across steps, sessions, and future tasks without filling its context with everything?

Time 25 minutes You will be able to design a memory system that retrieves useful information, saves the right information, and avoids stale or noisy memory Prerequisites Unit 11
Read this first — memory is not the same as context

An agent's context is the information currently available inside its working window.

Memory is information stored so that it can be retrieved later when it becomes useful again.

A good memory system does not remember everything. It remembers the right information, retrieves it at the right time, and keeps irrelevant history out of the agent's active context.

12.1 Context, Memory, and Knowledge are different

These three ideas are related, but they solve different problems. Confusing them creates bloated and unreliable agents.

Context vs. Memory vs. Knowledge
Concept What it means Example
Context Information currently available to the model while it is reasoning. The current conversation, tool results, instructions, and files opened during this task.
Memory Information saved from previous interactions or execution so it can be used later. "This project uses PostgreSQL." "The user prefers CSV output."
Knowledge External information the agent can search or retrieve when needed. Product documentation, company policies, research papers, manuals, or a knowledge base.
A simple way to remember the difference

Context = what is on the desk right now.

Memory = notes saved from previous work.

Knowledge = the library you can search when you need more information.

12.2 Four useful layers of agent memory

Layer 1
Working Memory

Information needed for the immediate reasoning step: recent messages, tool outputs, temporary calculations, and the current plan.

Layer 2
Task State

Progress that must survive across multiple execution steps: completed subtasks, current status, pending actions, checkpoints, and intermediate results.

Layer 3
Long-Term Memory

Durable information worth remembering beyond the current task: preferences, project conventions, recurring facts, successful decisions, and reusable lessons.

Layer 4
External Knowledge

Documents and reference material that are searched when needed rather than permanently placed inside the active context.

12.3 Short-term memory vs. long-term memory

Two different jobs
Dimension Short-Term / Working Memory Long-Term Memory
Lifetime Current task or session Future sessions or future tasks
Purpose Keep the current task coherent Reuse valuable information later
Typical content Current goal, recent messages, temporary results, open subtasks Stable preferences, project rules, reusable decisions, recurring facts
Main risk Context bloat Stale or incorrect memory

12.4 Memory is more than a Vector Database

A Vector Database is useful when an agent needs semantic similarity search, but it is only one possible memory storage mechanism.

Choose storage based on the type of information
Key-Value Store
Best for direct facts such as preferred_language = English or default_currency = BDT.
Relational Database
Best for structured records, relationships, timestamps, permissions, statuses, and audit history.
Vector Store
Best when information needs to be found by semantic similarity rather than an exact identifier.
Event Log
Best for recording what happened over time: actions, decisions, tool calls, failures, and checkpoints.
Files / Documents
Best for durable project instructions, specifications, reports, and human-readable reference material.
Do not start with "Which Vector DB should I use?"

Start with a better question: "What information must the agent remember, for how long, and how will it retrieve it?"

Storage technology comes after the memory policy.

12.5 The complete memory lifecycle

A useful agent memory system needs both a read policy and a write policy.

New Task → Retrieve Candidate Memory → Filter for Relevance → Reason & Act → Decide What Is Worth Saving → Persist Memory

Notice that the agent does not automatically load every old memory and it does not automatically save every output. Both sides require selection.

12.6 The Memory Read Policy

Before retrieving memory, the agent should ask:

  1. Is previous information actually useful for this task?
    Some tasks should start clean.
  2. Which memory scope applies?
    User-level memory, project-level memory, task-level memory, or organization-level memory?
  3. How should the memory be retrieved?
    Exact lookup, metadata filter, semantic similarity, chronological search, or a combination?
  4. Is the retrieved information still valid?
    Check timestamps, source, confidence, and whether newer information overrides it.
  5. How much should enter the context?
    Bring back the smallest amount of memory needed to make the next decision.

12.7 The Memory Write Policy

Saving everything is not memory. It is logging.

Before storing something as reusable memory, ask:

Good candidates for memory

Stable project conventions, recurring preferences, confirmed environment details, reusable decisions, successful fixes, and durable workflow rules.

Usually poor candidates

Temporary debugging output, one-time calculations, unverified assumptions, outdated values, raw logs, duplicate history, and every sentence from every conversation.

12.8 Why memory systems fail

Common memory failure modes
Failure What happens Better design
Memory Pollution Too much low-value information is saved. Add a strict write policy and confidence threshold.
Stale Memory An old fact is treated as if it is still current. Store timestamps, source information, expiry rules, and replacement logic.
Scope Leakage Memory from one user or project influences another. Separate memory namespaces and enforce access scope.
False Memory An inference or model-generated guess is stored as fact. Distinguish confirmed facts from inferred information.
Context Flooding Too many retrieved memories are inserted into the prompt. Rank, filter, summarize, and limit retrieved memory.
No Forgetting Strategy Memory grows forever even when information becomes irrelevant. Add expiration, superseding, deletion, and archival policies.

12.9 Worked example — a Coding Agent

Imagine an agent helping a developer maintain the same project for six months.

What the agent may remember

Project: Commerce Dashboard

Stable fact: Backend database is PostgreSQL.

Project convention: New frontend pages use React and Tailwind.

Reusable decision: Authentication tokens are stored in session storage rather than local storage for this application.

Known issue: Pricing page previously failed because of a routing configuration error.

Now imagine the user says: "Add another protected dashboard page."

The memory flow could look like this:

New Request → Retrieve Project Memory → Filter Relevant Facts → Use React + Tailwind + Existing Auth Pattern → Implement & Test → Save New Durable Decision
What should NOT be retrieved

The agent does not need last month's terminal logs, an unrelated CSV analysis, every previous code diff, or every message from every conversation.

Good memory reduces context. Bad memory recreates context bloat somewhere else.

12.10 Memory and Multi-Agent Systems

Unit 11 introduced Supervisor and Worker Subagents. Memory becomes even more important in that architecture.

A practical separation
Supervisor
Holds the user goal, orchestration state, important project memory, and final decision context.
Worker Subagent
Receives only the task-specific context it needs, performs the work, and returns a condensed result.
Memory Layer
Stores durable information that should survive after temporary worker contexts disappear.

This allows temporary reasoning to disappear without losing durable project knowledge.

12.11 A better agent memory architecture

User / Task → Supervisor → Memory Retrieval → Reason / Delegate / Act → Evaluate Result → Memory Write Decision ↺
The key design principle

Retrieve only what is useful. Persist only what is worth remembering.

Memory should make future reasoning easier, not turn every future prompt into a replay of the past.
