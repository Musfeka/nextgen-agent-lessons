Agentic RAG & Knowledge Retrieval

When an agent does not already know enough, how should it decide what to search, where to search, whether the evidence is useful, and when to stop?

Time 30 minutes You will be able to design an agentic retrieval workflow that searches selectively, evaluates evidence, retries intelligently, and answers from grounded information Prerequisites Unit 12
The core idea

RAG stands for Retrieval-Augmented Generation.

Instead of forcing the model to answer only from information already inside its context, a retrieval system can search external knowledge and bring relevant evidence into the context.

Agentic RAG adds decision-making around that process. The agent can decide whether retrieval is needed, choose a source, improve the search query, evaluate results, retry when necessary, and stop when enough evidence has been collected.

13.1 Memory and RAG solve different problems

Unit 12 introduced memory. Memory and retrieval are connected, but they are not the same thing.

Memory vs. RAG
Dimension Memory RAG / Knowledge Retrieval
Main question What useful information from previous work should the agent remember? What external information should the agent retrieve for this task?
Typical information User preferences, project decisions, previous task state, recurring facts Documentation, policies, reports, research papers, manuals, databases
Primary purpose Continuity Evidence and knowledge
Typical trigger Previous information is relevant to the current task The current context does not contain enough reliable information
Simple mental model

Memory: "What have I learned from previous work?"

RAG: "What information should I look up now?"

13.2 Fixed RAG vs. Agentic RAG

A conventional RAG application often uses a predefined retrieval pipeline. That is useful and may be all that many applications need.

Agentic RAG becomes useful when the system needs to make decisions about retrieval itself.

Fixed RAG
Predefined Retrieval Pipeline

The application follows a known sequence such as: receive query → retrieve documents → send retrieved context to the model → generate answer.

Agentic RAG
Adaptive Retrieval

The agent can decide whether retrieval is necessary, choose a retrieval strategy, inspect the evidence, rewrite the query, use another source, or stop when enough information has been found.

Use a simpler RAG pipeline when

The source is known, questions are predictable, one retrieval step is usually enough, and the cost of additional reasoning would add little value.

Consider Agentic RAG when

Questions are complex, several sources may be needed, retrieval quality varies, queries need decomposition, or the system must verify evidence before answering.

13.3 The Agentic Retrieval Loop

Instead of treating retrieval as a single search call, an agent can treat it as a controlled reasoning loop.

User Question → Need Retrieval? → Plan Search → Retrieve Evidence → Evaluate Evidence → Enough? → Answer

If the evidence is weak, the agent can loop:

Weak Evidence → Rewrite Query → Try Better Source → Retrieve Again ↺
Agentic does not mean search forever

Every retrieval loop should have a budget and stopping condition.

Otherwise the agent can waste time, money, tokens, and context on searches that are no longer improving the answer.

13.4 Step 1 — Decide whether retrieval is needed

The first retrieval decision should often be: "Do I need to search at all?"

Possible decisions
No Retrieval
The current context already contains enough information to complete the task.
Retrieve Memory
Previous project or user information is needed.
Retrieve Knowledge
External documents, databases, manuals, or knowledge bases are needed.
Use Another Tool
The task needs calculation, code execution, an API, database query, or another capability rather than document retrieval.

13.5 Step 2 — Understand the information need

Before searching, the agent should identify what information is actually missing.

  1. Identify the target.
    What fact, explanation, comparison, procedure, or evidence is required?
  2. Identify constraints.
    Does the answer depend on date, product version, region, department, document type, or another filter?
  3. Identify the best source.
    Which knowledge source is most likely to contain reliable evidence?
  4. Determine whether the question should be decomposed.
    A complex question may require multiple smaller searches.

13.6 Query Decomposition

Complex questions often contain several information needs. Trying to solve all of them with one retrieval query can produce weak results.

Example user question

"Compare our current refund policy with last year's policy and explain what changed for international customers."

An agent could decompose that into:

Find Current Refund Policy + Find Previous Policy + Extract International Rules → Compare Changes
Why decomposition helps

Each search now has a clear information target. Results can be evaluated independently before the final comparison is produced.

13.7 Query Rewriting

The user's wording is not always the best retrieval query. The agent may need to rewrite it without changing its meaning.

Examples of query improvement
User wording Possible retrieval query Reason
"Why does login fail sometimes?" authentication intermittent login failure session token Adds domain-specific search terms.
"What changed?" refund policy revision changes 2025 2026 Adds subject and time constraints.
"How do I configure it?" product-name version configuration setup documentation Resolves ambiguous wording using known context.

13.8 Source Routing

A strong retrieval agent does not send every question to the same search system.

Route the question to the best source
Product Documentation
Setup instructions, configuration, API behavior, feature descriptions
Internal Knowledge Base
Company procedures, policies, team documentation, decisions
Database
Structured records, transactions, inventory, users, operational data
Web Search
Public or rapidly changing information when external search is appropriate
Memory
Previous user preferences, project conventions, and durable decisions
Source quality matters

Retrieval is not successful merely because the system found text related to the query.

The agent must also consider authority, freshness, scope, relevance, and provenance.

13.9 Retrieval strategies

Different search methods find different kinds of information. A good system may combine several methods.

Common retrieval strategies
Strategy Good for Example
Keyword Search Exact terms, identifiers, error codes, names "HTTP 429"
Semantic Search Meaning-based matching when wording may differ "Unable to access account" matching documents about login problems
Metadata Filtering Restricting results by date, version, department, author, region Only documents for Product v4
Hybrid Retrieval Combining lexical and semantic signals Exact product code + conceptual similarity
Reranking Reordering candidate results after an initial retrieval step Selecting the best 5 chunks from 30 retrieved candidates

13.10 Chunking and Context Quality

Retrieval systems usually do not send an entire knowledge base to the model. Documents are commonly divided into smaller retrievable units, often called chunks.

Useful chunks

Preserve enough surrounding context to understand the meaning, section, subject, and source.

Poor chunks

Split information in the middle of an idea, remove essential headings, or return isolated sentences with no useful context.

Retrieval quality is not only an embedding problem

Document structure, chunk boundaries, metadata, query quality, filtering, reranking, and source selection all affect the final result.

13.12 What if retrieval fails?

An agentic retrieval system needs a recovery strategy.

Poor Results → Diagnose Why → Rewrite Query → Change Filter / Source → Retrieve Again

Possible fallback actions include:

  • Rewrite the search query.
  • Break the question into smaller searches.
  • Remove an overly restrictive filter.
  • Add a missing metadata filter.
  • Try keyword search instead of semantic search.
  • Try semantic search instead of exact keyword search.
  • Search a different authorized knowledge source.
  • Ask the user for missing information when necessary.
  • Return an explicit "insufficient evidence" result instead of guessing.
Self-correction does not mean inventing evidence

If retrieval repeatedly fails, the agent should eventually stop.

A trustworthy agent can say: "I could not find enough evidence to support that answer."

13.13 Conflicting Evidence

Sometimes retrieval succeeds but different sources disagree. That creates a different problem.

  1. Identify the conflict.
    Do not silently combine contradictory claims.
  2. Compare authority.
    Prefer the source that is authoritative for the question.
  3. Compare dates and versions.
    One source may simply be outdated.
  4. Check scope.
    Different rules may apply to different products, countries, teams, or customer types.
  5. Expose unresolved disagreement.
    If the conflict cannot be resolved, explain that clearly instead of choosing arbitrarily.

13.14 Provenance and Citations

The agent should retain enough metadata to know where important evidence came from.

Useful provenance metadata

Source: Customer Refund Policy

Section: International Orders

Version: 4.2

Updated: 2026-06-10

Document ID: POLICY-REFUND-042

This makes it easier to:

  • cite evidence,
  • debug incorrect answers,
  • detect outdated documents,
  • compare conflicting sources,
  • and audit important decisions.

13.15 Retrieval Budgets and Stop Conditions

Agentic retrieval needs boundaries. More retrieval is not automatically better.

Useful retrieval limits
Budget Example
Maximum Search Attempts Retry at most three times.
Maximum Retrieved Chunks Keep only the strongest five pieces of evidence.
Time Budget Stop retrieval after the allowed execution window.
Evidence Threshold Stop once the answer is sufficiently supported.
Fallback Condition If the trusted knowledge base has no evidence, return uncertainty instead of continuing indefinitely.

13.16 Common Agentic RAG failure modes

What can go wrong?
Failure What happens Better design
Unnecessary Retrieval The agent searches even when the answer is already in the current context. Add a retrieval decision step.
Poor Query The search does not describe the real information need. Rewrite or decompose the query.
Wrong Source The agent searches somewhere that cannot reliably answer the question. Add source routing.
Context Flooding Too many chunks are passed to the model. Filter and rerank results before generation.
Stale Evidence Old documentation overrides newer information. Use version and freshness metadata.
Unsupported Answer The model makes claims that retrieved evidence does not support. Grade evidence and ground claims explicitly.
Infinite Retrieval Loop The agent keeps rewriting and searching. Add budgets and stop conditions.

13.17 Worked example — Technical Support Agent

User question

"Our application started returning authentication errors after yesterday's deployment. What changed and how should we fix it?"

A well-designed agent could reason through the retrieval task like this:

  1. Determine that retrieval is needed.
    The answer depends on project-specific, recent deployment information.
  2. Decompose the question.
    Search deployment changes, authentication configuration, and relevant error documentation.
  3. Route searches.
    Use deployment logs for changes, internal documentation for configuration, and product documentation for error behavior.
  4. Retrieve candidate evidence.
  5. Grade and rerank evidence.
    Keep only information related to the affected deployment and authentication system.
  6. Compare evidence.
    Check whether yesterday's configuration differs from the previously working configuration.
  7. Answer with evidence.
    Explain the likely cause, identify the relevant change, and propose a fix supported by the retrieved material.
Question → Deployment Search + Auth Docs + Error Reference → Evidence Comparison → Grounded Fix

13.18 Memory + RAG + Tools

A capable agent may combine all three.

Example architecture
Memory
"This project uses PostgreSQL and React."
RAG
Retrieve the project's current database migration and authentication documentation.
Tool
Run tests, inspect database state, query logs, or execute code.
Agent
Decide which capability is needed, combine the results, evaluate them, and choose the next action.
The full picture

Memory provides continuity.

Retrieval provides external knowledge.

Tools provide actions and observations.

The agent decides how to use them together.

Final takeaway

Agentic RAG is not simply: "Give an LLM a Vector Database."

It is a controlled workflow in which the agent can:

Decide → Search → Evaluate → Refine → Verify → Stop → Answer

The goal is not maximum retrieval. The goal is the minimum reliable evidence required to complete the task well.
